# BotC-AI 产品全量功能文档

## 文档定位

本文描述 BotC-AI 的完整目标产品，而不是按时间追加的变更记录。具体单次需求以 `doc/modify/` 为实现与验收依据；本文在每次能力变化后重写，始终保持为连贯的全量定义。

当前产品版本为 `0.1.0`，已完成固定魔典源码基线和本项目测试基础设施，尚未进入规则内核与 Agent 业务能力开发。文中标记“目标”的能力尚未实现，交付顺序见[长期里程碑规划](../milestone/roadmap.md)。

## 产品愿景

BotC-AI 让用户直接在浏览器中发起严格遵循桌游规则的《染·钟楼谜团》在线对局。系统继承 townsquare 的虚拟魔典和实时房间能力，由房主浏览器运行 AI 说书人与可选数量的 AI 玩家，使人数不足、学习规则、测试剧本和 AI 自主对战都能在同一产品中完成。

产品第一阶段以“规则正确、信息隔离、完整可玩”为核心；第二阶段以“可评测、可训练、自博弈提升”为核心。

首个规则内核里程碑完整支持三个基础官方剧本《暗流涌动》《黯月初升》《梦殒春宵》，以及另行冻结清单内的旅行者、传奇角色和奇遇角色。这里的“完整支持”表示确定性流程、角色能力与结构化说书人裁量均可在无 LLM 条件下运行，不等同于遗留 UI 中已有的展示数据。

M1 规则范围还统一收录中文官方《术语汇总》的 80 个术语、《角色能力类别总览》的 31 个类别和《重要细节》的 7 个规则主题。跨页面重名内容共用规范概念，不复制成互相冲突的定义；每个概念明确属于内核规则、说书人裁量或参考概念。当前 110 个范围内角色与能力类别的官方可核验关联一并冻结，中文类别页未列出的角色保留空关联，不根据角色能力正文推测补全。

## 产品原则

### 规则正确优先

游戏必须严格遵循当前选定规则集的官方规则。能被代码确定判断的规则由规则内核执行，LLM 不得擅自改变；只有官方规则明确交给说书人判断的平衡、叙事和信息选择才由 AI 说书人决策。

### 私密信息最小可见

每个参与者只看到其按规则应知的信息。AI 玩家与人类玩家在信息权限上等价，不能因为运行在房主浏览器中而获得魔典真相、他人私聊或其他 Agent 的记忆。

### 人类与 AI 使用同一游戏协议

人类点击或输入形成的动作，与 AI 通过 Skill 工具提交的动作使用同一命令、校验和事件链。产品不维护一套绕过规则的“AI 快捷通道”。

### 浏览器是 Agent 主机

房主浏览器负责 Agent 调度、上下文构建、Skill 执行、LLM 调用、私密记忆和规则检索。会话后端只中继必要的在线消息，不运行 AI，也不保存模型密钥与完整私密状态。

### 可解释、可重放、可接管

关键状态变化记录为领域事件并可回放。AI 的工具调用、规则依据和失败原因可供房主审计；房主可以暂停 Agent、撤销尚未生效的操作，并在异常时人工接管。

## 用户角色

- 房主：创建在线房间、配置模型与 AI 席位、运行权威魔典、控制对局和查看运行状态。
- 人类玩家：通过链接加入房间，认领席位，接收私密身份和说书人消息，参与交流、提名、投票与角色行动。
- AI 说书人：读取真相视图，按照规则配置并推进对局，在裁量范围内生成信息与叙事，处理所有参与者的公开/私密交互。
- AI 玩家：占用普通玩家席位，读取该席位视图，自主交流、记录、推理、行动、提名和投票。
- 旁观者：仅在房主允许时查看公开对局信息，不读取隐藏身份或私密交流。

## 对局形态

产品支持以下组合：

- AI 说书人和全部人类玩家。
- AI 说书人和任意比例的人类/AI 混合玩家。
- AI 说书人与全部 AI 玩家，用于演示、回归、自博弈和训练数据生成。

“任意数量 AI 玩家”指从 0 到当前规则、剧本和产品席位上限允许的全部玩家席位；AI 不会突破桌游本身的人数与旅行者等限制。

## 完整用户流程

### 房间与模型配置

房主打开魔典后可以创建本地或在线对局，选择剧本、规则版本、玩家人数、席位类型和 AI 配置。每个 AI 席位可使用默认模型配置，也可覆盖模型、温度、预算和思考策略。

供应商配置至少覆盖 OpenAI、Claude、DeepSeek、火山方舟和本地部署 LLM。界面在保存前验证地址、模型能力、工具调用支持和连接状态；密钥默认只保留在房主设备上，并清楚展示浏览器直连可能产生的风险。

### 加入与席位管理

人类玩家通过房间链接加入并认领允许的席位。房主可将未认领席位设为 AI、把 AI 席位移交给人类，或在安全阶段把断线的人类席位交给 AI。席位转换必须保留该席位的合法认知与公开历史，但不能泄露原控制者的设备私密数据。

### 开局配置

AI 说书人根据玩家数、剧本、角色配置规则和设置修正提出角色组合。确定性规则内核校验角色类型数量、设置修正、相克与重复限制。房主可在开局前审阅或要求重新生成；确认后系统随机分发身份，并为每个席位构造独立认知视图。

### 夜晚阶段

规则内核生成本夜合法行动顺序和待处理任务。AI 说书人按顺序通过私密通道唤醒对应人类或 AI 玩家，收集选择，校验目标并结算能力。醉酒、中毒、死亡、角色变化、持续效果和相克规则影响由状态与规则层处理；需要说书人提供真假信息或平衡选择时，由 AI 在合法候选内决策。

夜晚结束后，系统发布按规则允许的死亡和公共信息，不公开来源或不应公开的细节。

### 白天交流

玩家可以公开发言、发起私聊或与说书人私聊。AI 玩家能主动选择交流对象、回应其他玩家、引用公开信息，并把自己的推理写入私有笔记。AI 说书人处理规则问答、白天角色能力、计时和必要的流程提示，同时避免通过措辞泄露隐藏状态。

所有规则问答均应基于版本化规则知识并可返回来源。角色处于醉酒或中毒状态也不会得到错误的规则解释。

### 提名、投票与处决

系统执行提名资格、被提名限制、投票资格、死亡票、票数效果、旅行者流放与处决阈值。人类使用界面操作，AI 玩家根据自身策略通过相同动作协议决定是否提名和投票。规则内核给出合法性与结果，AI 说书人负责主持表达。

### 结束与复盘

在任何可能触发胜负的状态变化后，规则内核检查通用及角色特殊胜利条件。对需要说书人裁量的特殊角色，AI 必须在规则允许范围内判断并记录依据。

对局结束后可以查看公开复盘；房主可以选择揭示完整魔典、AI 决策摘要和事件时间线。玩家私聊、玩家笔记和模型隐藏推理默认不公开。可导出的训练数据必须经过明确授权、脱敏和字段筛选。

## 在线魔典能力

继承并持续兼容 townsquare 的核心能力：

- 公开城镇广场与说书人魔典切换。
- 官方与自定义剧本加载、自定义角色和图标。
- 玩家席位、身份分发、存活状态、提醒标记、夜间顺序和角色参考。
- 在线会话、席位认领、实时同步、延迟展示和断线重连。
- 提名、投票、锁票、投票历史和主持控制。
- 旅行者、传奇角色及相克信息的展示基础。

初始 townsquare 源码作为固定快照保留，不再补建全量旧行为基线。后续新增能力必须带测试；修改遗留 UI 行为时，应为受影响范围增加回归测试。公共线上服务器不得作为本项目开发测试环境。

首期产品使用纯中文界面，剧本、角色、规则、阶段、动作、提示、错误、Agent 状态和帮助内容采用中文官方名称。界面信息架构、快捷键和整体视觉交互优先参考[集石钟楼官方魔典](https://clocktower.gstonegames.com/grimoire/)，并为 AI、权限、无障碍和响应式需求保留必要调整空间。英文环境和完整国际化能力在中文版本稳定后另立需求。

开发模式的会话客户端只使用本机 WebSocket 中继；生产构建必须显式配置受控的 `wss:` 地址，否则在线会话保持禁用且不回退公共服务。本地中继只承担旧协议的开发验证，不代表正式中继已经完成权限、隐私或部署评审。

## 通用 Agent 框架

Agent Runtime 在房主浏览器中为每个 Agent 创建独立运行实例，统一提供：

- 结构化消息与角色系统提示词。
- 按角色装配的 Skills 与有类型工具。
- 可取消的模型调用、流式输出、超时、重试和限流。
- 每 Agent 独立的短期上下文、摘要和持久记忆。
- 工具调用审批、权限校验、幂等、审计和错误恢复。
- Token、延迟、费用和失败率统计。
- 对局暂停、单 Agent 暂停、人工接管和从事件检查点恢复。

Agent Runtime 不决定桌游规则，也不直接持有可写魔典；它只根据授权视图推理并向领域命令总线提交工具调用。

## AI 说书人

AI 说书人由说书人系统提示词与说书人 Skills 组成。目标 Skills 包括：

- `session-communication`：向全部、指定阵营或指定席位发送公开/私密消息，等待回应，管理超时。
- `grimoire-read`：读取完整魔典、夜间队列、规则任务和事件历史。
- `grimoire-command`：提交设置、标记、状态、角色、死亡、复活、流程和结算命令，由规则内核校验。
- `rules-search`：检索中文官方规则、角色说明、相克与勘误，返回来源和版本。
- `storyteller-adjudication`：在规则明确允许裁量时，从合法候选中做平衡、信息真假和叙事决定。
- `game-control`：开始、暂停、恢复、进入阶段、发起提名流程和宣布结束。

AI 说书人遇到规则资料冲突或无法安全裁量时必须暂停相关动作、说明不确定性并请求房主处理，不能编造规则。

## AI 玩家

AI 玩家由玩家系统提示词与玩家 Skills 组成。目标 Skills 包括：

- `player-communication`：公开发言、私聊其他玩家、回复说书人和管理待回复消息。
- `player-action`：选择角色能力目标、提名、投票、使用死亡票和执行其他合法玩家动作。
- `private-notes`：维护仅当前 Agent 可读的事实、主张、时间线、怀疑和计划。
- `player-view`：读取自己的身份认知、存活状态、公开魔典、收到的信息和可执行动作。
- `rules-search`：查阅官方规则和角色说明，但不能借检索获取本局隐藏信息。
- `strategy`：对公开/私有认知进行推理，安排交流和行动；策略不能突破工具权限。

每个 AI 玩家都具有独立上下文和存储命名空间。批量调度需要保证发言节奏可用，避免所有 AI 同时刷屏或阻塞房主浏览器。

## 规则知识与检索

规则知识以离线同步和版本化索引为主。首要来源为集石运营维护的《染·钟楼谜团》中文官方资料，包括钟楼百科中的规则、角色说明、相克、勘误和发布信息。中文资料缺失时再使用对应英文官方资料，补充内容必须翻译为中文并保留英文来源、页面修订、内容哈希、翻译版本和复核状态。

规则知识正文与规则范围清单分离。范围清单只保存规则包身份、中文规范名称、稳定 ASCII ID、概念目录、实现责任、来源指针、角色分类关联和完整性哈希，不复制官方规则正文。对局及后续规则实现必须引用清单中的规范概念 ID，不能以页面标题或显示名称充当状态与事件标识。

知识同步流程需要：

- 从配置的入口发现规则、剧本和角色页面。
- 提取正文，清理导航、脚本和展示噪声，规范化内部链接与图片地址。
- 保存来源 URL、页面修订、页面更新时间、抓取时间、语言、内容哈希以及英文补充的中文翻译版本和复核状态。
- 将内容切分并建立可在浏览器加载的检索索引。
- 在检索结果中返回中文片段、标题、来源与版本；英文缺失补充同时保留对应英文来源指针。
- 对页面结构变化、重复文件名、重定向、限流和离线失败提供测试与报告。

中文官方资料与英文补充发生语义冲突时，无论英文资料是否更新，中文结论始终进入规范规则包；英文差异只进入同步报告，不能由同步工具静默覆盖。对相邻实验项目只复用上述思路，不复制其正则抓取器或知识目录结构；本项目应使用可测试的 HTML 解析、清洗和索引模块重新实现。

## LLM 供应商与本地模型

统一 Provider 接口至少表达：模型发现或配置、普通/流式消息、工具调用、结构化输出、取消、超时、重试、用量和错误分类。

支持模式包括：

- 浏览器直接调用允许跨域访问的云端 API。
- 连接用户自己控制的 OpenAI 兼容网关，用于不支持浏览器直连的供应商。
- 连接房主设备或局域网中的本地部署 LLM。

Provider 的接入方式不改变 Agent 位于房主浏览器这一事实。远端只执行模型推理或协议转发，不保存对局控制权。产品必须提示把 API Key 放在浏览器中的风险，并允许会话结束时清除凭据和缓存。

## 数据、隐私与安全

- 真相魔典只在房主权威状态中存在；发送给玩家的数据必须先生成座位权限视图。
- 会话消息按公开、阵营、点对点、玩家到说书人等频道分类并校验接收者。
- AI 玩家笔记、提示词、模型请求和完整返回默认只在房主设备保存。
- API Key 不进入 Vuex 持久化、事件日志、WebSocket 消息、导出对局或错误上报。
- Wiki 和玩家消息都是不可信输入，进入 Prompt 前需标记数据边界；其中的指令不能提升工具权限。
- 对局导出分为公开复盘、房主审计和训练数据三种明确格式，不默认混合私密内容。

## 可靠性与性能

- 房主浏览器应在单个 Agent 超时或 Provider 故障时保持 UI 可用，并允许重试、跳过或人工接管。
- Agent 调度必须有并发上限、请求队列和取消机制，避免多 AI 对局耗尽浏览器资源或供应商限额。
- 所有状态命令幂等或带唯一 ID，断线重发不能重复结算能力或投票。
- 在线会话以房主为权威；远端玩家重连后从权限过滤的快照与后续事件恢复。
- 可恢复的对局需要周期检查点与事件日志，浏览器崩溃后恢复时重新校验不变量。

## 可访问性与语言

- 所有新增交互支持键盘与触控，重要状态不只依赖颜色表达。
- 私密消息、等待状态、AI 正在思考、错误和人工接管入口具有可读文本与辅助技术标签。
- 首期产品只提供中文环境，不把遗留英文内容直接暴露为正式产品文案；规则索引明确区分中文事实与英文缺失补充。英文界面、运行时语言切换和完整国际化框架后续另立需求。

## 质量与验收体系

当前测试基础设施使用 Jest 承载单元、Vue 组件、场景和本地中继集成测试，使用 Playwright Chromium 承载端到端测试。本地与 GitHub Actions 使用 Node.js 22、锁文件安装和相同的分层门禁；端到端测试同时启动本地前端与只监听回环地址的中继，阻断外部请求，不连接公共会话或真实 LLM。遗留代码暂不设置全仓覆盖率阈值，新增或修改的可测试业务逻辑必须随需求提供有效测试。

- 单元测试覆盖规则内核、权限视图、命令校验、事件归约、Provider 适配和知识解析。
- 官方规则示例转为可读场景测试，覆盖醉酒/中毒、死亡、角色变化、持续效果、相克与特殊胜负。
- 属性测试验证状态不变量与事件重放一致性。
- 集成测试覆盖房主、人类客户端、AI 席位和 WebSocket 中继。
- 端到端测试覆盖建房、加入、分发、完整昼夜、提名投票、断线恢复和结束复盘。
- Agent 行为使用确定性假模型做回归；真实模型只用于显式评测，不作为合并门禁的唯一判断。

## 第二阶段：自博弈与强化学习

第二阶段不直接使用第一阶段的私密真实对局训练。系统先建立可复现模拟环境、版本化策略、裁判指标和训练数据协议，再允许多个 AI 自主对战。

核心能力包括：

- 无 UI 或加速模式的确定性对局环境。
- 对局种子、规则版本、模型版本、Prompt/Skill 版本和完整合法事件记录。
- 按阵营胜率、规则违规率、信息泄漏率、策略多样性、成本和延迟进行评测。
