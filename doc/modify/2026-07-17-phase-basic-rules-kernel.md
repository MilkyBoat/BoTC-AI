# M1-R4 阶段与基础规则内核

## 元信息

- 状态：本地完成
- 创建日期：2026-07-17
- 关联里程碑：[M1-R4 阶段与基础规则内核](../milestone/roadmap.md#m1规则内核事件模型与权限视图)
- 负责人：Codex

## 背景与问题

M1-R2 已建立房主浏览器中的版本化命令、事件、原子提交、幂等回执与重放底座，M1-R3 已建立参与者权限视图；但当前领域协议只会把对局初始化为 `initialized`，没有真实的准备、首夜、白天、夜晚和结束状态，也没有席位生死、常规处决或常规胜负。后续提名投票、角色能力、完整规则包和中文魔典 UI 如果各自在组件或 Agent 中推进流程，将重新造成同一规则多套实现、死亡与处决语义混淆、胜负遗漏及事件不可重放。

M1-R4 需要把不依赖具体角色能力的流程规则写入确定性内核：从准备状态开始对局，严格推进首夜与昼夜，记录普通玩家和旅行者的生死，区分“被处决”与“因处决而死亡”，并在每次会影响胜负的死亡后立即计算常规胜负。提名资格、计票和处决候选推导属于 M1-R5；死亡保护、角色变化、特殊胜负与阻止胜利等角色效果属于 M1-R6 至 M1-R11，不能在本需求中用调用方布尔参数提前模拟。

## 目标、用户价值与成功指标

- 房主侧可信调用方能通过统一命令完成准备、开局、首夜、白天、其他夜晚和结束的基础流程。
- 席位顺序、角色类型、生死和当天常规处决成为权威状态；组件、Agent 和测试不能直接改状态。
- 普通死亡、复活、处决及阶段变化产生可重放事件，并保留固定中文官方来源标识。
- 常规处决只允许在白天发生一次；执行后无论目标是否因处决死亡，都结束白天并进入夜晚。
- 所有恶魔死亡时善良获胜；除旅行者外存活玩家不超过两名时邪恶获胜；两项同时满足时善良优先。
- 命令重试、修订冲突、批次原子性、事件导出与恢复继续使用 M1-R2 语义。
- 新逻辑通过单元、场景、覆盖率、Lint、生产构建和完整 Chromium 端到端门禁，不连接外部生产会话或真实 LLM。

## 用户与使用场景

- 房主建立对局后提交已核定的席位和角色类型，内核校验基础结构并从 `setup` 进入 `first-night`。
- 说书人完成当前阶段的全部任务后请求推进；内核只允许 `first-night -> day -> night -> day` 的固定序列并维护昼夜编号。
- 后续角色能力框架在完成目标、保护与角色效果判定后，使用基础死亡或复活命令改变生死；M1-R4 不替角色能力决定目标是否应死亡。
- M1-R5 在完成提名和计票后调用同一常规处决命令；M1-R4 只校验当前是否为白天、当天是否已处决并完成处决—死亡—胜负—入夜的原子结算。
- 每次死亡后内核检查常规胜负并在同一命令批次中结束对局；调用方不能忘记或延后检查。
- 导出的日志在新实例中重放后得到相同阶段、编号、席位生死、处决记录、胜方和修订。

## 规则来源与已确认结论

本需求使用 M1-R1 固定在 `m1-ruleset-scope.json@0.2.0` 中的中文官方来源。为核对正文，开发时通过已完成的 Wiki 同步工具读取以下固定修订，临时正文只放在被 Git 忽略的 `.work/m1-r4-phase-basic-rules/`：

- `zh-wiki-glossary`，修订 `6017`：白天、夜晚、首个夜晚、存活、死亡、复活、处决、旅行者与常规胜负。
- `zh-wiki-ability-execution`，修订 `6312`：每个白天一次常规处决、处决后立即入夜、处决与因处决死亡的区别，以及死亡后检查胜负的时序。
- `zh-wiki-ability-special-win-loss-condition`，修订 `5406`：所有恶魔死亡、非旅行者仅剩两名、同时满足常规胜负时善良优先。
- `zh-wiki-ability-death-immunity`，修订 `5964`，以及 `zh-wiki-ability-resurrection`，修订 `5754`：免死不产生死亡，复活使死亡玩家重新存活；具体保护和重新获得角色能力留给角色框架。

由上述固定来源与既有里程碑边界可确定：

- 对局从首个夜晚开始，首夜结束进入第一个白天，之后白天与其他夜晚交替。
- 存活与死亡是互斥状态；对已经死亡的席位再次结算“死亡”没有状态变化，基础死亡命令应拒绝而不是伪造第二次死亡事件。
- 已死亡目标仍可能被处决；“被处决”成立，但“因处决而死亡”不成立，白天仍会结束。
- 常规处决与处决造成的死亡是同一命令的连续领域事实；如果死亡触发常规胜负，则先结束游戏，不再进入夜晚。
- 常规胜负只计算真实角色类型和真实生死，不受玩家认知影响。旅行者不计入邪恶的存活人数阈值，但旅行者的加入、离开、公开角色、隐藏阵营与流放仍全部留给 M1-R10。
- M1-R4 只实现常规胜负。角色特殊胜负、胜负阻止、主谋/镜像双子/小怪宝等优先级以及角色变化由后续规则包提供新的版本化结算流程，不允许 M1-R4 接受 `preventWin`、`specialWinner` 或类似任意覆盖字段。

## 已确认范围与边界

### 范围

- 将领域协议从 `0.1.0` 演进为 `0.2.0`，为权威状态增加明确的基础游戏字段，而不是任意扩展容器。
- `game.create` 之后进入 `preparing/setup`，席位为空，昼夜编号为零，尚无处决和胜方。
- 新增开局、推进阶段、死亡、复活和常规处决命令及对应领域事件。
- 开局负载包含稳定席位 ID、连续顺序与角色类型；角色类型只到 `townsfolk`、`outsider`、`minion`、`demon`、`traveler`，不包含具体角色 ID、阵营认知或能力。
- 开局至少有三名非旅行者玩家且至少一名恶魔；M1-R4 不校验标准人数对应的角色类型配比、设置修正、相克或具体角色重复。
- 仅 `host` 与 `system` 审计主体能提交本需求的控制命令。未来 AI 说书人必须先通过受信命令网关映射为获授权控制意图，不能只凭 `actor.kind = agent` 获得权限。
- 所有规则事件保存 `ruleSourceId`，来源修订由固定规则集身份与 M1-R1 清单共同确定。
- 增加权威状态语义不变量；命令批次提交和事件流恢复都在每个成功命令边界验证，不允许留下已满足常规胜负却仍为运行中的状态。
- 完整保留 M1-R2 的严格 Schema、不可变返回、乐观修订、幂等、原子提交、回执和重放行为。

### 非范围

- 不实现角色选择、随机分发、标准人数角色配比、设置修正、相克、具体角色 ID、认知身份或夜晚行动队列。
- 不实现提名资格、被提名限制、投票、计票、死亡票、平票、即将被处决候选或旅行者流放；这些属于 M1-R5 与 M1-R10。
- 不实现醉酒、中毒、保护、免死、能力失效、死亡触发能力、角色/阵营变化、持续效果或说书人裁量任务。
- 不实现特殊胜负、阻止胜利、胜负反转或角色能力之间的结算优先级。
- 不接入遗留 Vuex、组件、WebSocket、浏览器持久化或 M1-R3 快照源；UI 接入属于 M1-R12，真实完整视图源要等角色与认知状态具备后再接入。
- 不新增 Agent、Prompt、Skill、Provider、外部 API 或真实模型测试。
- 不修改线上环境、外部 Wiki、公共会话服务、生产配置和真实对局数据；不 Push、不创建 PR、不部署。

## 状态模型与基本不变量

协议 `0.2.0` 权威状态包含：

- `lifecycle`：`preparing`、`running` 或 `ended`。
- `phase`：`setup`、`first-night`、`day`、`night` 或 `ended`。
- `dayNumber`：准备与首夜为 `0`，第一个白天为 `1`，以后每次从夜晚进入白天加一。
- `nightNumber`：准备为 `0`，首夜为 `1`，每次从白天进入其他夜晚加一。
- `seats`：按从 `1` 开始的连续顺序保存唯一席位 ID、角色类型和 `alive`。
- `executionToday`：当前白天的常规处决结果，包含日号、席位及是否因处决死亡；进入新白天时清空。
- `winner`：未结束时为 `null`；结束后保存 `alignment`、`reason` 和决定该结果的事件序号。

任何成功命令边界都必须满足：

- `preparing` 只能对应 `setup`、空席位、零昼夜编号、空处决和空胜方。
- `running` 只能对应首夜、白天或夜晚，至少三名非旅行者与至少一名在场恶魔，胜方为空，且没有已经满足但未结算的常规胜负。
- `ended` 只能对应 `ended`，胜方非空且与席位生死事实一致。
- 席位 ID 与顺序唯一，顺序严格为 `1..N`；事件不能修改对局 ID、规则集、种子或既有席位身份。
- 首夜为 `dayNumber=0/nightNumber=1`；白天满足两者相等；其他夜晚满足 `nightNumber=dayNumber+1`。
- `executionToday` 只能引用存在的席位与当前日号；同一白天不能出现第二次常规处决。
- 善良常规胜利的事实为没有任何存活恶魔；邪恶常规胜利的事实为非旅行者存活数不超过二；两者同时成立时只能记录善良获胜。

## 命令、事件与正常流程

### `game.create` / `game.created`

保持 M1-R2 的规则集与种子负载，但归约出的当前状态改为 `preparing/setup`。这是协议破坏性演进的一部分，旧 `0.1.0` 流不按新语义静默重放。

### `game.start` / `game.started`

- 仅准备阶段可执行。
- 负载严格包含基础席位列表；处理器与归约器都校验唯一 ID、连续顺序、非旅行者人数和恶魔存在。
- 事件把全部席位初始化为存活，进入 `running/first-night`，编号为第 `1` 夜。

### `phase.advance` / `phase.advanced`

- 仅运行中可执行。
- `first-night -> day` 时进入第 `1` 天；`day -> night` 时进入下一个夜号；`night -> day` 时进入下一个日号。
- 白天可以在没有处决时主动结束；进入新白天清空前一日处决记录。
- 准备与结束阶段不能推进，调用方也不能指定目标阶段或编号。

### `player.kill` / `player.died`

- 仅运行中可执行，目标必须存在且当前存活。
- 调用方提供稳定 `causeId` 及可选来源 ID，用于后续角色规则追踪；它不能携带“是否应死亡”的裁量开关。
- 死亡事件把席位改为死亡；处理器根据事件后的真实状态计算常规胜负，必要时在同一批次追加 `game.ended`。

### `player.revive` / `player.revived`

- 仅运行中可执行，目标必须存在且当前死亡。
- 事件只恢复基础生死；重新获得能力、进场能力、限次能力与角色状态重置属于 M1-R6 及具体角色规则包。
- 已结束对局不能通过复活回滚胜负。

### `execution.resolve` / `player.executed`

- 仅运行中的白天可执行，且当前白天尚未进行常规处决；目标必须存在，存活与死亡均可。
- 先记录 `player.executed`。目标存活时追加 `player.died`；目标已死亡时不伪造死亡事件，并把 `died` 记录为 `false`。
- 若死亡触发常规胜负，追加 `game.ended`；否则追加 `phase.advanced` 并立即进入夜晚。
- 候选如何由提名和票数产生不属于本命令，M1-R5 必须复用此入口而不是自行修改生死或阶段。

### `game.ended`

- 只由基础规则处理器生成，调用方没有“宣布任意胜方”的公共命令。
- 事件保存善良/邪恶胜方与 `all-demons-dead` / `two-alive` 原因。
- 对局结束后，除相同命令的幂等重试外，所有新基础规则命令均被拒绝。

## 失败、恢复与取消路径

- 非控制主体、错误阶段、重复开局、未知席位、重复死亡、重复复活、当天第二次处决和结束后的新动作形成可持久化领域拒绝回执，不产生事件。
- 非法信封、额外字段、重复席位、跳跃顺序、没有恶魔、非旅行者不足三人、伪造事件来源和损坏事件负载失败关闭；连信封都不合法的输入不占用命令 ID。
- 处决命令的“处决、可能死亡、胜负或入夜”是一个原子事件批次；任一候选事件或最终不变量失败时全部不提交。
- 幂等重试返回原回执；新命令遇到修订冲突后由调用方读取最新状态并使用新命令 ID 重新表达意图。
- 本模块是本地同步纯函数，不存在网络超时、限流或异步取消；调用方关闭页面后的恢复和持久化属于 M5-R4。

## 权限、可见性与隐私

- 权威席位角色类型、完整命令、事件和拒绝详情只留在房主可信边界。
- 本需求的领域命令先限制为 `host/system`；席位、旁观者和普通 Agent 不能直接提交。
- 生死、阶段、被处决和最终胜方属于公开事实，但本需求不新增网络或 UI 序列化路径。后续视图事件投影必须正向构造公开字段，不能把 `game.started` 中的隐藏角色类型原样广播。
- 状态和事件不得包含真实玩家姓名、私聊、AI 私有笔记、Prompt、模型请求/返回、API Key、Cookie、证书或设备凭据。

## Agent、Skill 与 LLM 约束

- 本需求不新增或运行 Agent、Prompt、Skill、工具与 Provider。
- 后续 AI 说书人必须经命令权限网关提交与人类房主相同的版本化命令；玩家 Agent 只能提交对应玩家动作，不能使用基础控制命令。
- 规则来源和同步正文是数据，不得改变命令权限、事件 Schema 或内核运行时。
- LLM 超时、限流、成本、流式输出和降级不适用；测试不得调用真实模型。

## 兼容、迁移与回滚

- 新状态字段和 `game.created` 归约语义使领域协议提升为 `0.2.0`；协议版本、Schema ID、命令、事件、回执和事件流信封同步提升。
- 当前领域协议尚未接入 UI、WebSocket、IndexedDB 或生产存档，没有需要迁移的真实 `0.1.0` 对局。`restoreDomainProtocol` 对旧流明确返回不支持版本，不静默补字段。
- M1-R3 视图协议仍为独立 `0.1.0`，其版本不随领域协议提升；固定测试事件使用当前领域协议版本重新验证。
- 回滚本需求只需回退本地提交；没有外部数据写入、线上副作用或远端分支变化。

## 验收标准

- Spec 中影响实现的待确认项清零，M1-R4 与 M1-R5、M1-R6 至 M1-R11、M1-R12 的边界无冲突。
- 创建后为 `preparing/setup`；合法开局为 `running/first-night`，席位全部存活且昼夜编号正确。
- 只允许首夜—白天—其他夜晚的固定循环；错误阶段、调用方指定目标和结束后推进均失败。
- 重复席位、跳跃顺序、少于三名非旅行者或没有恶魔的开局失败，并且处理器与重放归约都不能绕过不变量。
- 普通死亡、重复死亡、复活、重复复活、未知席位和结束后变更有稳定结果；每次真正死亡后都检查常规胜负。
- 常规处决一天最多一次，处决存活目标会同时造成死亡，处决死亡目标不会造成第二次死亡；未结束时处决立即入夜。
- 最后一名存活恶魔死亡时善良获胜；非旅行者存活数降到二或以下且仍有存活恶魔时邪恶获胜；同时满足时善良获胜。
- 事件流完整重放得到相同状态、事件、回执与幂等结果；篡改来源、顺序、阶段、席位、胜方或命令批次边界时失败关闭。
- 新规则模块与测试独立 ESLint 为零错误零警告，并设置至少 80% 语句/函数/行、70% 分支的覆盖率门禁。
- `npm run test:coverage` 与 `npm run test:ci` 通过；最终差异只包含 M1-R4 代码、测试和连贯文档更新，创建本地提交且不 Push。

## 测试矩阵

- Schema：所有新增状态、命令和事件正反例、额外字段、非法角色类型、来源 ID、胜方与原因组合。
- 开局：合法普通席位与含旅行者席位；重复 ID/顺序、跳跃顺序、缺少恶魔、非旅行者不足三人、重复开局和非控制主体。
- 阶段：首夜到第一天、白天到其他夜晚、夜晚到下一天、多轮循环、无处决结束白天、错误阶段和结束后推进。
- 生死：日夜死亡、重复死亡、复活、重复复活、未知席位、死亡原因记录和不可变返回。
- 处决：存活目标、死亡目标、每天一次、错误阶段、处决后入夜、处决致胜不入夜，以及处决与因处决死亡事件的区别。
- 胜负：最后恶魔死亡、两名非旅行者存活、旅行者不计数、同时满足时善良优先、未满足时继续。
- 权限：`host/system` 正向，`seat/observer/agent` 负向；不能通过负载指定胜方、阶段或跳过胜负。
- 原子与重放：多事件处决、处理器/归约器失败、幂等、修订冲突、导出恢复、旧版本拒绝、事件删改和成功命令边界不变量。
- 回归：M1-R2 原有协议测试、M1-R3 视图泄漏测试、现有组件/场景/中继与 Chromium E2E 全部通过。

## 实现与验收结果

- 新建 `src/domain/rules/`，提供五个严格命令构造器、基础规则来源常量、命令/事件定义、常规胜负纯函数和状态语义不变量；公开入口不会暴露直接归约或任意状态补丁能力。
- 领域协议由 `0.1.0` 提升为 `0.2.0`。严格 Schema 新增阶段、昼夜编号、基础席位、生死、当天处决、胜方，以及 `game.start`、`phase.advance`、`player.kill`、`player.revive`、`execution.resolve` 对应负载。
- `game.create` 当前进入 `preparing/setup`；`game.start` 校验基础席位后进入首夜。阶段只按首夜、白天、其他夜晚循环，进入新白天清空当天处决记录。
- 普通死亡、复活与常规处决使用专用事件。处决存活玩家产生“被处决、因处决而死亡、胜负或入夜”事件批次；处决已死亡玩家只记录被处决并入夜。
- 每次真正死亡后按固定中文官方来源计算常规胜负，善良条件先于邪恶条件；对局结束后不能通过新命令推进、复活或改写胜方。
- 命令原子提交前及事件流恢复的每个成功命令边界验证基础状态不变量；删去致胜批次的 `game.ended`、伪造席位或篡改阶段会失败关闭。`0.1.0` 旧事件流明确返回不支持版本。
- 测试先行红灯已确认：实现前新增单元与场景套件均因 `@/domain/rules` 不存在而失败；实现后新增 24 条测试全部通过，并保留 M1-R2/M1-R3 回归。

## 风险与待确认项

- 当前没有影响实现的待确认项。阶段名称已与 M1-R3 视图契约中的 `setup/first-night/day/night/ended` 对齐；中文官方固定来源明确了阶段、处决与常规胜负；M1-R5 及角色规则包边界由路线图和既有 Spec 明确。
- M1-R4 的角色类型只为常规胜负提供最小真实事实，不表示对应具体角色、能力和标准设置已实现。后续规则包必须在开局前增加更严格的角色与设置校验。
- 立即常规胜负与后续角色触发之间存在扩展风险。后续 M1-R6 至 M1-R11 需要以新协议版本显式加入受约束的前置触发与特殊胜负流程，不能给当前命令增加任意“跳过胜负”开关或原地改变 `0.2.0` 语义。
