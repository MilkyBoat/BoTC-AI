# 提名与投票规则

## 元信息

- 状态：本地完成
- 创建日期：2026-07-17
- 关联里程碑：[M1-R5 提名与投票规则](../milestone/roadmap.md)
- 负责人：Codex

## 背景与问题

M1-R2 已建立版本化命令、事件、幂等回执与重放协议，M1-R3 已建立 Storyteller、Public、Seat 与 Observer 的权限视图，M1-R4 已实现准备、首夜、昼夜、生死、常规处决与常规胜负。但权威状态尚不知道谁在当天提名或被提名、投票窗口走到哪个席位、死亡票是否已经使用、谁当前即将被处决，以及旅行者流放是否通过。若 UI、玩家 Agent 或 AI 说书人各自计算这些结果，会导致断线重发重复消耗死亡票、平票与最高票结果不一致，甚至绕过每天一次提名、每天一次被提名和旅行者不能被常规处决等规则。

M1-R5 需要把不依赖具体角色能力的提名、顺时针计票、死亡票、最高票/平票/过半、处决候选和旅行者流放写入确定性规则内核，并复用 M1-R4 的常规处决与死亡入口。玩家动作只表达自己的提名或当前计票决定；流程控制、代理记录和结算由受信房主/系统命令完成。角色能力对提名、票数、处决、死亡保护或额外处决的修改仍属于 M1-R6 至 M1-R11，不能通过任意权重或跳过校验参数提前模拟。

## 目标、用户价值与成功指标

- 存活玩家可以每天发起一次常规提名；任何玩家每天最多被常规提名一次，允许自我提名，已死亡玩家可以被提名。
- 同一时间最多存在一个常规提名或流放表决流程；常规投票按席位顺时针依次记录，并以被提名者为最后一位。
- 存活玩家可在每次常规提名中投票；死亡玩家在死亡后只有一张死亡票，成功计入任意一次常规投票后立即永久消耗，复活并再次死亡时重新获得一张。
- 票数至少为一、达到当前存活玩家数量一半的向上取整且严格高于当天其他提名，才形成唯一“即将被处决”候选；同最高票时没有候选，更高票可以替换此前候选。
- 结束提名时，存在候选则只能通过 M1-R4 常规处决入口处决该候选；没有候选才允许无处决入夜。
- 旅行者不能进入常规提名或常规处决；任何存活或死亡玩家均可提议流放旅行者、支持流放且不消耗死亡票。达到全体在场玩家数量一半的向上取整即流放成功，流放造成死亡但不是投票、提名或处决，不结束白天且不受角色能力影响。
- 命令重试、修订冲突、断线代理、原子事件批次和日志恢复沿用领域协议语义；相同日志重放得到相同窗口、游标、票数、死亡票、候选、流放和阶段结果。
- 公共投影只发布公开流程事实，不泄露权威命令信封、主体凭证、拒绝详情或隐藏阵营；旁观策略可继续隐藏逐票席位明细。
- 新逻辑通过针对性单元/场景测试、覆盖率、Lint、生产构建与完整 Chromium 端到端门禁，不连接公共会话服务、真实 LLM 或生产数据。

## 用户与使用场景

- 存活的人类或 AI 席位通过相同的 Seat 动作协议发起常规提名；房主/系统可以在断线、超时或线下代操作时按明确席位代理提交。
- 说书人在辩护结束后打开常规投票窗口。内核从被提名者的下一个顺时针席位开始，逐席要求记录赞成或不赞成，最后记录被提名者。
- 当前轮到的席位只能记录自己的决定；房主/系统可以代记。完成全部席位后由房主/系统关闭窗口并确定票数和当天候选。
- 如果后续提名获得更高票数且满足门槛，则替换候选；如果与当前最高票相同，则当天暂时没有候选；更低票数不改变候选。
- 提名阶段结束时，调用方对唯一候选提交既有 `execution.resolve`；没有候选时提交既有 `phase.advance` 结束白天。
- 任意存活或死亡席位可在白天提议流放一名存活旅行者。支持窗口为同时表态，不采用常规顺时针计票；房主关闭窗口时，尚未表态视为不支持。
- 流放通过后旅行者死亡并获得死亡票，白天继续且仍可进行常规提名、常规处决及其他旅行者流放。

## 规则来源与已确认结论

本需求以 M1-R1 的 `m1-ruleset-scope.json@0.2.0` 为规则范围身份。开发时通过 Wiki 同步工具读取以下固定中文官方修订，临时正文仅位于被 Git 忽略的 `.work/m1-r5-nomination-voting/`：

- `zh-wiki-glossary`，修订 `6017`：处决门槛、即将被处决、提名、投票、投票标记、流放和旅行者的基础定义。
- `zh-wiki-important-details`，修订 `4183`：允许自我提名和给自己投票、死亡玩家不能提名且只有死亡票时才能投票、角色能力优先于通则以及角色能力不能影响流放。
- `zh-wiki-ability-nomination`，修订 `5887`：同一时间一个提名、存活者才能提名、每天每人发起/被提名各一次、流放不计入提名。
- `zh-wiki-ability-vote`，修订 `5936`：活人可为任意多次提名投票、死亡票在成功计数时消耗、最高票/平票/过半/至少一票，以及某次票数结算后不因之后状态变化重算。
- `zh-wiki-ability-execution`，修订 `6312`：每天最多一次常规处决、处决与死亡的区别，以及处决后立即入夜。
- 中文官方《旅行者》页面固定修订 `5590`、MediaWiki SHA-1 `9b34f7f0cb188fde0b59f6401495d365a4b24cf2`：任何存活或死亡玩家都可提议或支持流放；支持人数门槛按全体玩家而非存活玩家计算；每名旅行者每天只可被提议流放一次；流放不消耗死亡票、不受能力影响、不算提名/投票/处决、不结束白天，成功时旅行者死亡。该页面是对清单内 `exile` 概念所指中文官方规则的固定补充，M2-R1 建立完整来源清单时应将其正式物化，不能在运行时读取动态页面。

由上述来源与既有里程碑边界可唯一确定：

- “等于或超过一半”对整数票数使用向上取整。常规投票分母为窗口打开时的存活玩家数量；流放分母为当前全部在场席位数量，包括死亡玩家与旅行者。
- 常规投票按顺时针统计并终止于被提名者，因此固定顺序为被提名者之后的下一个席位开始，绕一圈后以被提名者结束。
- 同一轮常规投票中每个席位最多被计数一次。活人赞成不消耗资源；死人赞成且被计入时消耗死亡票，不论最终提名是否形成候选。
- 票数结算时立即固定该提名结果。后续死亡、复活或存活人数变化不会按新门槛回算已经结算的提名；当天最高原始票数仍参与后续提名的严格比较。
- 平票是“没有唯一最高票”，会清除先前候选；之后严格高于该最高票的新结果可以产生新候选。
- 旅行者可以作为存活玩家发起普通提名并参与普通投票，但不能被普通提名或普通处决。旅行者通过单独流放流程死亡；被流放后仍在对局中且与其他死者一样获得一张死亡票。
- 每名旅行者每天最多被提议流放一次，但同一玩家每天可以提议任意数量的不同旅行者；流放提议不占用普通提名次数。
- 流放支持不是角色意义上的投票，不能触发投票能力，也不能被投票权重、管家限制或死亡票修改。M1-R5 的流放负载因此不接受权重、门槛覆盖或能力来源字段。

## 已确认范围与边界

### 范围

- 将领域协议从 `0.2.0` 演进为 `0.3.0`，严格扩展状态、命令、事件与重放 Schema。
- 席位状态增加公开的 `deadVoteAvailable`；存活席位为 `false`，每次真实死亡变为 `true`，复活时清为 `false`，死亡投票被计入后变为 `false`。
- 权威状态增加当天提名结果、当前常规提名/投票窗口、当天最高票、当前处决候选、当天流放结果与当前流放支持窗口。
- 新增打开提名、打开常规投票、按顺序记录投票、关闭常规投票、打开流放、设置流放支持、关闭流放的严格命令和可重放事件。
- `phase.advance` 在存在活动窗口或处决候选时拒绝；`execution.resolve` 只能处决当前唯一候选且禁止旅行者，继续复用 M1-R4 的处决—死亡—胜负—入夜原子批次。
- 普通死亡、复活、常规处决和成功流放正确维护死亡票；死亡票使用与投票记录在同一事件归约中完成。
- Seat 主体只能替自己的席位发起提名、记录轮到自己的投票、提议流放或设置自己的流放支持；Host/System 可以代理明确席位并控制窗口开关与结算。
- 扩展 M1-R3 的公共状态与领域事件投影，使死亡票、提名、投票结果、候选和流放结果按正向字段构造；Observer 的 `includeVoteDetails=false` 继续移除逐席明细。
- 所有自动化规则事件保存固定 `ruleSourceId`；来源修订由本 Spec、M1-R1 规则范围与事件流规则集身份共同固定。

### 非范围

- 不实现管家、官员、乞丐、枪手、窃贼、巫毒师、法官、主教、屠夫、替罪羊等具体角色对提名、投票、处决或死亡的修改。
- 不实现票数权重、负票、额外提名、强制投票、投票资格覆盖、免门槛、额外处决、处决替代、死亡保护或任意说书人改票参数。
- 不实现旅行者加入、主动离开、具体角色 ID、隐藏阵营、角色能力、角色变化或旅行者与普通角色互换；这些属于 M1-R10 及具体角色规则包。
- 不实现遗留 Vuex、组件、WebSocket 或浏览器持久化接入；中文魔典 UI 接入属于 M1-R12，Agent 主持和玩家超时策略属于 M3/M4。
- 不新增 Prompt、Skill、Provider、真实 Agent 或 LLM 测试。
- 不修改线上环境、公共中继、外部 Wiki、生产配置或真实对局数据；不 Push、不创建 PR、不部署。

## 状态模型与基本不变量

协议 `0.3.0` 在 M1-R4 状态之上增加：

- `seats[].deadVoteAvailable`：只有死亡席位可以为 `true`；存活席位必须为 `false`。
- `nominationsToday`：按结算顺序保存 `nominationId`、日号、提名者、被提名者、票数、门槛、赞成席位、结果与是否成为结算后的候选。
- `activeNomination`：为空，或保存当前提名 ID、日号、提名者、被提名者、`defense/voting/ready-to-close` 阶段、固定投票顺序、游标、门槛及已经按顺序记录的决定。
- `highestNominationVotes`：当天全部已结算常规提名的最高原始票数，未结算任何提名时为 `0`。
- `executionCandidate`：为空或保存当前唯一即将被处决席位及其票数；平票时为空，但最高票数仍保留。
- `exilesToday`：按结算顺序保存流放 ID、提议者、旅行者、支持者、门槛与是否成功。
- `activeExile`：为空，或保存流放 ID、日号、提议者、旅行者和当前每席支持决定；未表态席位在关闭时按不支持处理。

任何成功命令边界必须满足：

- 准备、首夜、夜晚与结束状态没有活动提名/流放、当天记录、最高票或处决候选；进入新白天时全部初始化为空或零。
- 同一时间不能同时存在常规提名和流放；活动提名与流放都只能存在于当前白天。
- 已结算常规提名的 ID、提名者和被提名者当天唯一；提名者在提名时必须存活，被提名者必须为非旅行者。
- 活动投票顺序精确覆盖全部席位一次，顺时针且最后为被提名者；已记录决定必须是该顺序的连续前缀。
- 死亡席位只有在死亡票可用时才能记录赞成；一旦记录即在同一事件中消耗，不能通过重放或重试二次消耗。
- `highestNominationVotes` 等于当天记录最大票数；候选存在时必须达到其当时门槛、至少一票、严格等于最高票且没有同票记录。
- 每名旅行者每天最多出现于一个流放结果或活动流放；普通席位不能成为流放目标。
- `execution.resolve` 的目标必须等于当前候选；常规处决后进入夜晚或结束游戏，并清除活动流程与候选。

## 命令、事件与正常流程

### `nomination.open` / `nomination.opened`

- 仅运行中白天、没有活动提名/流放且当天尚未处决时可执行。
- 负载严格包含 `nominationId`、`nominatorSeatId` 与 `nomineeSeatId`。
- 提名者必须存在、存活且当天尚未提名；被提名者必须存在、不是旅行者且当天尚未被提名；允许两者相同。
- Seat 主体的 ID 必须等于提名者席位；Host/System 可代理。事件进入 `defense` 阶段，不自动打开投票。

### `vote.open` / `vote.opened`

- 仅 Host/System 能在活动提名的 `defense` 阶段执行。
- 内核根据当前席位顺序生成从被提名者下一席开始、以被提名者结束的唯一 `votingOrder`，并固定 `threshold=ceil(存活席位数/2)`。
- 活动窗口进入 `voting`，游标指向首个席位。调用方不能传入顺序、门槛、权重或资格覆盖。

### `vote.record` / `vote.recorded`

- 负载包含提名 ID、当前席位 ID 与布尔 `support`；只能记录游标所指席位。
- Seat 主体只能记录自己的决定；Host/System 可代理。赞成的存活席位正常计票；赞成的死亡席位必须有死亡票并在事件归约时消费；不赞成不消费。
- 每次记录推进一个游标。到达末尾后窗口进入 `ready-to-close`；已记录决定不能修改或取消。

### `vote.close` / `vote.closed`

- 仅 Host/System 能关闭已完成全部席位记录的窗口。
- 内核统计赞成席位，按至少一票、固定门槛和当天严格最高票计算结果，并原子更新历史、最高票、候选与活动窗口。
- 同票清空候选但保留最高票；低票保持候选不变；严格更高且达门槛产生或替换候选；严格更高但未达该次门槛只提高最高票并保持无候选。

### `execution.resolve` 与 `phase.advance`

- `execution.resolve` 在 M1-R5 中必须没有活动窗口、存在候选且目标精确匹配候选；旅行者永远拒绝。通过后继续使用 M1-R4 的处决、可能死亡、胜负或入夜事件批次。
- `phase.advance` 从白天进入夜晚时必须没有活动窗口且没有候选；这表达当天无人被处决。首夜与夜晚推进保持 M1-R4 语义。
- 调用方没有“忽略候选”“指定其他目标”或“直接清空候选”的命令。

### `exile.open` / `exile.opened`

- 仅运行中白天、没有活动提名/流放且当天尚未处决时可执行；普通提名候选可以继续保留。
- 负载包含 `exileId`、`proposerSeatId` 与 `travelerSeatId`。提议者可以存活或死亡；目标必须是当前存活旅行者且当天尚未被提议流放。
- Seat 主体 ID 必须等于提议者席位；Host/System 可代理。提议不消耗或要求普通提名资格。

### `exile.support.set` / `exile.support-set`

- 任意在场席位可在活动流放窗口设置或修改自己的布尔支持决定；Seat 只能设置自己，Host/System 可代理。
- 存活、死亡和旅行者席位规则相同；设置支持不读取或消费死亡票，也不按顺序推进。

### `exile.close` / `exile.closed`

- 仅 Host/System 可随时关闭活动流放；未表态席位视为不支持。
- 门槛为 `ceil(全部在场席位数/2)`。达到门槛时事件记录流放成功并追加基础死亡事件；旅行者获得死亡票，白天、普通提名次数、普通票数和处决候选均保持。
- 未达到门槛只记录失败结果；同一旅行者当天不能再次被提议。流放成功或失败都不产生处决事件、不触发投票能力且不结束白天。

## 权限、可见性与隐私

- Host/System 能控制窗口、代理明确席位和结算；Seat 只能提交与自身绑定的玩家动作。Observer 与裸 `agent` 主体不能提交本需求命令；未来 AI 玩家由受信网关映射为对应 Seat 主体，AI 说书人映射为受控 Host/System 意图。
- 提名者、被提名者、顺序、每席举手、票数、门槛、候选、旅行者身份、流放支持和结果均为桌面公开事实；死亡票可用状态也公开。
- 权威命令 ID、期望修订、主体 ID、拒绝详情、完整回执和审计信息只留在房主可信边界。视图事件只正向构造公开字段，不转发领域事件信封。
- Observer 的只减策略可以隐藏逐票/逐支持席位，但不能伪造票数、门槛、候选或最终结果。Seat/Public/Storyteller 看到相同公开事实。
- 状态、事件和视图不得包含真实姓名、连接凭证、设备状态、私聊、隐藏阵营、AI 笔记、Prompt、模型请求、API Key、Cookie 或证书。

## 交互、失败恢复与取消路径

- 非法阶段、并发活动窗口、重复提名者/被提名者、旅行者进入普通提名、错误投票顺序、死亡票不足、提前关票、重复流放目标、普通目标进入流放、候选不匹配和越权主体形成可持久化中文拒绝回执，不产生事件。
- 命令信封与负载严格拒绝额外字段。客户端断线重发同一命令 ID 返回原回执；同 ID 不同内容报幂等冲突；过期修订返回拒绝，调用方读取新状态后用新命令 ID 重新表达仍然有效的意图。
- Seat 在自己的普通投票时隙断线或超时，由 Host/System 代理记录 `support=false` 后继续；不能静默跳过游标。流放窗口关闭时未表态自然视为不支持，不需要逐席代理。
- 已接受的提名、逐票决定和流放结果不可删除或回滚，避免事件日志与公开桌面事实分叉。UI 应在提交前确认；操作错误的管理纠正协议不属于 M1-R5，不能用通用状态补丁伪造取消。
- 活动常规投票或流放期间，M1-R4 的死亡、复活、阶段推进和处决命令拒绝，以冻结本次窗口的顺序、门槛和资格。未来角色能力若需在计票中插入死亡或修改票数，必须由 M1-R6+ 以新协议版本定义明确事件时序。
- 本模块为本地同步纯函数，不存在网络限流或异步取消。页面关闭后的持久化恢复属于 M5-R4；当前事件导出与同版本重放必须无损恢复活动窗口。

## Agent、Skill 与 LLM 约束

- 本需求不新增或运行 Agent、Prompt、Skill、Provider 与真实模型。
- AI 玩家未来只能从 SeatView 读取公开流程和自己的合法动作，并以 Seat 主体提交；不能读取其他席位私密状态或使用 Host/System 命令。
- AI 说书人未来通过受控命令工具打开/关闭窗口和代理超时，不得直接修改权威状态、票数或死亡票。
- 规则来源正文为不可信数据，不能改变工具权限、命令 Schema 或运行时控制流。
- LLM 供应商差异、超时、限流、成本与降级不适用；测试使用确定性命令和事件，不调用真实模型。

## 兼容、迁移与回滚

- 新状态与命令使领域协议提升为 `0.3.0`；协议版本、Schema ID、命令、事件、回执和事件流信封同步提升。`0.2.0` 事件流明确返回不支持，不静默补充死亡票或提名状态。
- 参与者视图协议按新增公开死亡票与当前领域事件投影同步演进；旧视图源必须显式使用旧实现，不把缺失字段解释为死亡票可用。
- 当前协议尚未接入 Vuex、WebSocket、IndexedDB 或生产存档，没有真实数据迁移；回滚只需回退本地提交。
- M1-R12 接入 UI 时必须消费命令、事件和权限投影，不能读取遗留 Vuex 投票字段作为规则事实。
- M1-R6+ 增加角色修改时需要新协议版本与旧日志回放测试；不能在 `0.3.0` 中增加任意 `voteWeight`、`ignoreThreshold`、`preventDeath` 等解释变化。

## 验收标准

- Spec 覆盖提名资格、每天次数、被提名限制、投票窗口与顺序、活人票、死亡票、平票/最高票/过半、处决/无人处决、旅行者流放、阶段接口、权限、断线、幂等、重放、角色能力与 UI 边界，且没有影响实现的待确认项。
- 合法自我提名、死亡目标被提名、重复提名者、重复被提名者、死亡提名者、旅行者普通提名和并发窗口得到唯一结果。
- 投票顺序从被提名者下一席顺时针开始并以被提名者结束；越序、重复、提前关闭和窗口外投票失败。
- 活人可在多次提名投票；死者只有死亡票可用时能赞成一次，赞成被计入即消费，反对不消费，幂等重试不重复消费，复活再死亡重新获得。
- 奇偶存活人数的向上取整门槛正确；至少一票、低票、严格高票、连续替换、两方/多方平票和平票后更高票正确维护候选。
- 有候选时不能无处决入夜，也不能处决其他席位或旅行者；无候选时可以正常入夜。候选处决继续满足 M1-R4 原子死亡、胜负和阶段语义。
- 任意活/死玩家可提议流放；活/死玩家可支持且不消费死亡票。门槛按全部席位计算，同一旅行者每天一次，成功流放造成死亡但不结束白天、不清除普通候选、不占普通提名/处决次数。
- 活动窗口阻止基础生死和阶段漂移；断线代理、修订冲突、同命令幂等、同 ID 冲突、导出恢复及篡改日志均有回归。
- Public/Seat/Storyteller 获得一致公开事实；Observer 隐藏逐票明细时仍看到真实总数、门槛和结果；任何投影不含主体 ID、回执或隐藏阵营。
- `src/domain/rules/` 与相关视图模块保持至少 80% 语句/函数/行、70% 分支门禁；针对性测试、`npm run test:coverage` 与 `npm run test:ci` 全部通过。
- 最终差异只包含 M1-R5 的 Spec、规则/协议/视图实现、测试和连贯文档更新；本地提交，不 Push、不合并。

## 风险与待确认项

- 当前没有影响实现的待确认项。固定中文官方提名、投票、术语、重要细节、处决与旅行者修订对本需求所有基础行为给出唯一结论；M1-R1 已确认中文优先和角色能力覆盖通则的版本策略。
- 常规计票期间的枪手死亡、官员/窃贼权重、管家资格、巫毒师门槛、屠夫额外提名、法官额外处决与保护死亡属于后续角色能力。`0.3.0` 主动冻结活动窗口中的基础生死变化，后续必须以版本化事件时序扩展，不能原地改变本版本重放结果。
- 中文官方《旅行者》修订 `5590` 尚未列入 M1-R1 的 39 个机器清单来源，但它是清单内 `exile` 规范概念的固定中文官方正文补充。本需求在代码事件中仍使用清单已有的 `zh-wiki-glossary` 来源 ID；M2-R1 完善来源清单时应补齐该页面及哈希，不影响 `0.3.0` 日志的确定性。
- 当前视图服务仍使用抽象视图源，遗留 UI 尚未由权威状态生成该源。M1-R5 只扩展协议和投影语义；真实 UI 适配与断线存档由 M1-R12/M5-R4 分别实施。
