# M1-R1 规则范围与版本策略

## 元信息

- 状态：本地完成
- 创建日期：2026-07-16
- 关联里程碑：[M1-R1 规则范围与版本策略](../milestone/roadmap.md#m1规则内核事件模型与权限视图)
- 负责人：Codex

## 背景与问题

M0 已建立固定源码基线、测试门禁和安全的本地会话环境。M1 将开始建设确定性规则内核、领域事件和权限视图，但在定义状态、命令或角色能力前，必须先冻结首个严格支持的规则范围以及规则升级方式。否则，同一对局可能因外部页面更新而改变行为，M1 各需求也可能分别采用不同的角色、人数或来源边界，导致事件无法稳定重放。

当前 townsquare 固定源码携带三个基础剧本、`Laissez un Faire` 和 130 个角色的英文展示数据。暗流涌动数据包含 13 个镇民、4 个外来者、4 个爪牙、1 个恶魔和 5 个旅行者；另有 13 个旧分类下的传奇角色。该固定数据只证明旧 UI 能展示这些内容，不代表名称、分类和规则仍与当前中文官方资料一致。例如源码仍把“暴风捕手”归为传奇角色，而当前中文官方资料已将其归入奇遇角色，因此旧数据不能成为新规则内核的事实来源。

本项目首期采用纯中文环境。产品名称、剧本名称、角色名称、规则正文、界面、提示、错误、Agent 提示词和面向用户的日志均优先使用中文官方名称。英文环境和完整国际化支持留待后续独立需求，不在 M1 中提前实现。

## 目标与成功标准

- 明确 M1 最终必须完整运行的三个基础官方中文剧本、角色集合和玩家人数。
- 明确旅行者、传奇角色、奇遇角色、实验性角色、自定义剧本、相克规则和特殊人数变体在 M1 的支持状态。
- 建立可供 M1-R2 及后续需求引用的不可变规则集标识、版本升级和对局固定策略。
- 明确中文官方资料的规范性、英文补充方式、冲突优先级、版本冻结方式和无法裁决时的处理方式。
- 把“旧 UI 可展示”“规则内核严格支持”“AI 说书人首发可主持”区分为三个不同概念。
- 为 M1 的 UI 适配需求明确中文官方魔典的参考边界，同时允许增加 AI、权限和无障碍所需的新交互。
- 形成可直接验收的支持矩阵；所有影响实现的待确认项清零后，才进入实现或完成状态。

## 用户与使用场景

- 房主以纯中文界面选择规则集并开始对局，能确认当前对局采用的精确规则版本、人数和角色范围。
- 人类或 AI 玩家提交动作时，规则内核只按对局固定版本校验，不受对局期间外部资料变化影响。
- 房主可以按已确认范围加入旅行者、传奇角色和奇遇角色；对应加入时机、公开信息、流放、胜负计数和特殊规则均由内核处理。
- AI 说书人只能在中文规则包明确交给说书人裁量的范围内决策；规则冲突或产品未支持的组合不能由 LLM 猜测补齐。
- 开发者实现状态、事件、权限视图和角色能力时，能从同一支持矩阵确定必须覆盖的规则及测试。
- 复盘或恢复旧对局时，系统能定位当时的规则包，不使用最新规则静默重算历史。

## 已确认需求

- M1 严格支持三个基础官方剧本：《暗流涌动》《黯月初升》《梦殒春宵》。使用中文官方名称“梦殒春宵”，不使用“梦陨春宵”。
- 三个剧本共包含 39 个镇民、12 个外来者、12 个爪牙和 9 个恶魔，共 72 个非旅行者角色。到 M1 完成时，全部角色的确定性规则和结构化说书人裁量必须可以在无 LLM 情况下完整运行。
- 支持 5 至 15 名非旅行者玩家，包括 5/6 人《暗流涌动》的官方小人数规则。
- M1 同时支持三个基础剧本对应的全部 15 个旅行者、12 个非实验性传奇角色以及中文官方页面当前列出的全部 11 个奇遇角色。
- 5/6 人对局不自动加入“玩具匠”。“玩具匠”若在最终传奇角色清单内，只能由房主按官方规则显式选择。
- 普通实验性角色、3 个实验性旅行者、2 个实验性传奇角色、自定义剧本和 `Laissez un Faire` 不属于 M1 严格支持范围。
- 旧 UI 中黯月初升、梦殒春宵、旅行者和其他角色数据在 M1-R1 保留，不在本需求隐藏或删除；可展示不等于被新内核严格支持。
- 首期只支持中文环境。中文官方名称和中文规则内容是规范事实；英文资料仅在中文资料不足且不与中文资料冲突时作为补充并翻译为中文。
- 可确定验证的流程、权限、规则和状态变化由确定性代码校验，LLM 不得绕过规则内核。
- 官方明确留给说书人的信息真假、平衡、模糊注册和开放式选择可以形成结构化裁量任务。
- 每条自动化规则必须保留来源标识，并覆盖正常、醉酒/中毒、死亡/失去能力、角色变化和相克场景中适用的测试。
- 规则版本必须进入权威状态和事件重放上下文；对局开始后不能静默切换规则语义。
- 采用不可变版本策略：开发期使用 `0.x`，M1 全量验收后发布 `1.0.0`；任何规则行为或来源语义变化都发布新版本，对局固定精确版本且不自动升级。
- 在线来源按固定页面修订、URL、抓取时间和内容哈希形成来源清单；不能稳定定位版本的动态资料只作交叉验证。
- 同一规则快照内，明确的官方勘误或相克特例优先于具体角色说明，具体角色说明优先于简写能力文本，具体能力文本优先于通用规则；同类别资料中明确的新修订覆盖旧修订。
- 中文与英文官方资料存在规则语义冲突时，无论英文页面是否更新，均以中文官方资料为准。英文差异只能进入同步报告，不能覆盖中文规则包。
- 官方资料没有明确答案时，确定性内核不得猜测。开发期存在未决冲突时不得发布规则包；运行期遇到无法安全裁定的情况应暂停相关动作并请求房主裁定，本局裁定不自动升级为规则事实。
- M1-R1 只交付决策文档、支持矩阵和不含规则正文的机器可读范围清单，不实现任何业务规则逻辑。
- M1-R1 不连接或修改线上对局、生产服务、生产配置或真实玩家数据。
- 项目使用场景已由用户确认为合规，本需求及后续开发不再将许可问题作为风险、待确认项或实现门禁。

## 范围

- 冻结 M1 中文规则集的剧本、人数、角色类型和角色 ID 范围。
- 为三个基础剧本、旅行者、传奇角色、奇遇角色、实验性角色、自定义剧本、汀西维尔、相克规则及未识别角色定义明确的支持策略。
- 定义规则集 ID、内部版本、来源清单版本和完整性标识的职责边界。
- 定义新对局、进行中对局、恢复对局和回放对局如何选择并固定规则版本。
- 定义中文官方来源类别、同类资料的新旧优先级、特例覆盖通则、英文补充及冲突升级流程。
- 定义官方规则更新的发现、翻译、评审、版本发布、兼容和旧版本保留原则。
- 建立文档化支持矩阵，并同步产品、架构、里程碑、知识目录和文档索引中的稳定结论。
- 提供只含规则包身份、中文显示名称、角色 ID、支持状态、来源指针和兼容信息的机器可读范围清单，不复制规则正文。
- 机器可读清单固定为 [`knowledge/rulesets/m1-ruleset-scope.json`](../../knowledge/rulesets/m1-ruleset-scope.json)，其结构由 [`knowledge/rulesets/ruleset-scope.schema.json`](../../knowledge/rulesets/ruleset-scope.schema.json) 约束。
- 将集石中文官方魔典登记为 UI 参考基线；具体 UI 实现与验收留给 M1 的 UI 适配需求。

## 非范围

- 不在 M1-R1 定义领域状态、命令、事件、归约器、幂等或重放文件格式；这些属于 M1-R2。
- 不实现说书人视图、公共视图、座位视图和旁观者视图；这些属于 M1-R3。
- 不实现阶段状态机、提名投票、流放或任何角色能力；这些由澄清后的 M1 后续需求承担。
- 不在本需求中删除或翻译全部旧 UI 数据，也不让 townsquare UI 直接使用新内核。
- 不决定 AI 说书人的审批粒度、提示词、Skills 或完整首发交互；这些属于 M2/M3。M3-R1 可以在 M1 严格规则范围内进一步缩小产品首发切片，但不能扩大规则范围。
- 不抓取或打包中文/英文官方 Wiki 正文、规则书、图片与角色素材；来源同步和知识包生成属于 M2-R1/M2-R2。
- 不支持普通实验性角色、中文独占同人角色、自定义剧本以及三个基础剧本以外的官方大型/小型剧本；中文资料站当前列出的游园惊梦、无名之墓、凶宅魅影等后续剧本不进入 M1 普通角色范围。
- 不实现英文界面、运行时语言切换、多语言资源框架或翻译管理后台；国际化在中文版本稳定后另立需求。
- 不发布、不 Push、不创建 PR，也不触发自动部署。

## 中文来源与版本策略

- 中文官方 Wiki 是规则正文、角色名称、角色分类和中文术语的首要来源。
- 集石中文官方魔典用于核对界面名称、角色展示、菜单结构、快捷键、角色能力表和夜晚顺序表；其动态运行状态不能单独成为确定性规则来源。
- 中文资料对某项事实已有明确结论时直接采用中文结论，不使用英文内容改写其语义。
- 中文资料完全缺少某条通用规则或角色交互时，才读取对应英文官方资料。补充内容必须先形成中文翻译，记录英文页面、修订、抓取时间、内容哈希、翻译版本和复核状态，再进入中文规则包。
- 中文与英文资料出现规则语义冲突时始终采用中文结论。即使英文修订时间更晚，也只记录差异并等待中文官方资料更新；不得据此改变中文规则包。
- 中文资料存在但表述不足以形成唯一确定性行为时，可以用英文资料帮助识别问题，但不能让英文结论覆盖中文语义。仍无法得到唯一且不冲突的中文结论时，按未决冲突处理：开发期阻断规则包发布，运行期暂停相关动作并请求房主裁定。
- 社区 Wiki、论坛、视频、聊天记录和本项目历史代码不能自动成为规则事实。中文独占同人内容即使出现在中文资料站，也必须与官方角色明确区分，默认不进入 M1。
- 每个规则包记录规则集 ID、精确版本、规范语言 `zh-CN`、来源清单版本和清单哈希。代码、JSON、事件协议和存档使用稳定 ASCII 标识；所有面向用户的名称、正文、提示、测试描述和文档使用中文。
- 规则包一经发布不可原地修改。新增角色属于次版本升级；既有范围内的规则修正属于修订版本升级；破坏状态、命令或回放兼容性属于主版本升级。无论版本级别如何，进行中和历史对局都固定原精确版本。

## 中文界面参考边界

M1-R1 不修改界面，但为后续 UI 适配确认以下方向：

- 所有可见标题、菜单、按钮、状态、角色、阵营、阶段、错误和帮助文本使用中文官方名称。
- 以集石中文官方魔典的全屏魔典、右上角分组菜单、白天/夜晚切换、角色能力表、夜晚顺序表、创建/加入小镇、座位环形布局和键盘快捷键作为信息架构与交互参考。
- 新增的 AI 说书人、AI 席位、审批、暂停、接管、模型状态和审计入口需要融入同一中文视觉语言，但不能为追求外观一致而牺牲权限提示、键盘操作、触控和无障碍要求。
- 不连接参考站点的线上小镇，不复制其运行状态或用户数据；设计核对仅使用公开页面。
- 中文官方魔典是术语、信息架构、主要交互、快捷键和整体视觉气质的设计基线，不要求像素级复制；AI、权限、无障碍和响应式需求可以调整布局。

## 交互与失败恢复

- M1-R1 本身不改变用户界面。旧 UI 能加载某剧本或角色，不表示新规则内核支持该内容。
- 后续规则集选择器必须用中文展示规则集名称、精确版本、支持状态、人数范围和特殊角色范围。
- 新对局只能选择本地存在且完整性校验通过的受支持规则包。未知或损坏规则包不得降级为“尽力运行”。
- 对局创建后固定精确规则版本；检测到新版本时只提示，不自动升级进行中对局。
- 恢复或回放时缺少原规则版本，应停止可写恢复并提供只读诊断；不得用新版本替代后继续写入。
- 对受支持范围内但资料冲突、实现缺失或状态无法安全判断的动作，应拒绝提交或暂停相关流程，并用中文说明原因和恢复入口。
- 取消、超时、断线和人工接管的具体事件语义不在 M1-R1 实现，由 M1-R2 及相关后续需求定义。

## 状态、事件与权限

M1-R1 只确定未来状态和协议必须表达的事实，不设计最终字段：

- 对局必须固定规则集 ID、精确内部版本、规范语言、来源清单版本和完整性哈希。
- 旅行者需要独立表达公开角色、隐藏阵营、加入/离开时机和是否为邪恶；传奇角色与奇遇角色需要独立分类，不能继续混入同一旧集合。
- 规则包不得包含 API Key、私聊、玩家笔记或本局隐藏身份。
- 规则版本、中文显示名称和公开特殊角色是公开元数据；旅行者阵营、具体角色真相、状态和裁量结果仍按权限视图过滤。
- 规则升级不修改既有事件。旧事件只能由其记录的规则版本重放。
- M1-R1 的机器可读清单只表达规则包身份、范围、来源指针和兼容信息，不提前定义 M1-R2 的领域协议。

## Agent、Skill 与 LLM 约束

- M1-R1 不运行 Agent、不新增 Skill、不调用真实 LLM 或 Provider。
- 后续系统提示词、Skills、工具说明、工具反馈、规则检索结果和人工审批界面均使用中文。
- AI 说书人和 AI 玩家读取的规则资料必须与当前对局固定规则版本一致，不能检索到更新版本后据此改变本局规则。
- AI 说书人只能处理规则包显式声明的裁量任务；不能为未支持角色、未知组合或来源冲突发明确定性结果。
- AI 玩家只能获得座位视图和公开的规则版本元数据，不能借规则检索获得本局隐藏信息。
- 真实供应商的超时、限流、成本和降级在本需求不适用；后续测试使用确定性假模型。

## 兼容、迁移与回滚

- M1-R1 不修改现有 Vuex 状态、浏览器存储、WebSocket 协议或存量魔典数据，因此不执行产品数据迁移。
- 旧 townsquare 英文角色与剧本数据暂时保留为遗留展示数据，并明确标记为非规则事实；中文化、分类迁移和入口限制由后续 UI 适配需求验收。
- 首个规则包发布后采用不可变版本；修正文案、来源元数据或行为都通过新版本发布，不原地覆盖已被对局引用的包。
- 规则实现可回滚到上一已验证版本；已创建对局继续引用原精确版本。无法保留旧实现时必须禁止可写恢复，而不是静默迁移。
- 官方资料更新不触发自动迁移。兼容性和迁移方案必须在每个规则包升级需求中单独说明并增加回放回归。
- M1 不建立英文资源与中文资源双轨；未来国际化需求需要从已稳定的中文事实模型中提取显示层资源，不能改变既有规则 ID 和事件语义。

## 实现计划

1. 先增加范围清单的失败单元测试，覆盖 Schema、精确角色集合、唯一 ID、稳定顺序、来源引用、席位边界和排除项。
2. 增加 JSON Schema 与 M1 机器可读范围清单，只保存规则包身份、中文显示名称、稳定 ASCII ID、支持状态、固定来源指针和兼容信息，不保存规则正文。
3. 运行范围清单单元测试并补齐负向用例，确认无效结构、重复 ID、损坏来源引用和越界人数会被拒绝。
4. 执行文档一致性检查、完整单元/组件/场景/集成测试、Lint、生产构建和 Chromium 端到端测试。
5. 重写本需求和路线图状态，确认差异只包含 M1-R1 后创建本地提交，不 Push。

## 实现结果

- 已增加 `knowledge/rulesets/m1-ruleset-scope.json`，以 `0.1.0` 版本冻结三个基础剧本的 72 个非旅行者角色、15 个旅行者、12 个非实验性传奇角色和 11 个奇遇角色，共 110 个定义。
- 已增加严格的 Draft-07 JSON Schema，限制规范语言、来源策略、席位范围、稳定 ASCII ID、中文显示名称、支持状态、排除项和完整性元数据；未知字段会被拒绝。
- 中文官方来源固定到暗流涌动修订 `2716`、黯月初升修订 `2731`、梦殒春宵修订 `5102`、传奇角色修订 `6229` 和奇遇角色修订 `5919`，并记录原始 Wikitext 的 SHA-256。
- 范围清单使用 `sorted-json-v1` 规范化算法计算完整性哈希，哈希范围是除 `integrity` 字段自身以外的完整清单。
- 已增加 11 个单元测试，覆盖 Schema、三个剧本、精确角色 ID、中文官方显示名称、稳定顺序、特殊角色分类、席位与语言策略、来源修订与引用、清单完整性、排除项和负向数据。

- `npm run test:coverage` 通过，共 29 个测试；`npm run test:ci` 通过，包括单元、组件、场景、集成、Lint、生产构建和 3 个 Chromium 端到端场景。Lint 为 0 错误、414 条遗留警告，低于 415 条预算。

## 测试方案

- 文档一致性检查：搜索路线图、产品、架构、知识目录和需求文档中的规则范围、角色分类、来源顺序与语言状态，确认没有互相冲突的表述。
- 支持矩阵检查：逐项核对暗流涌动、黯月初升、梦殒春宵、旅行者、传奇角色、奇遇角色、实验性角色、自定义剧本、人数和相克策略均有明确值。
- 中文术语检查：检查面向用户的剧本、角色类型和规则术语使用中文官方译名，不再把 Loric 作为正文名称。
- 来源检查：每个规范性来源都有稳定修订标识策略；动态 URL 不被当作不可变版本；英文补充都具有中文翻译与双向来源记录。
- 版本场景推演：覆盖新建对局、进行中发现更新、旧版本恢复、缺失版本回放、规则包损坏和来源冲突。
- 权限与安全检查：确认规则版本元数据不含密钥或本局隐藏信息，旅行者阵营没有进入公共规则元数据。
- 机器可读清单测试：增加 Schema 单元测试、重复 ID 负向测试、来源引用缺失测试、角色分类测试和稳定序列化快照测试。
- 回归检查：M1-R1 不改业务代码；运行新增清单校验单元测试、Lint 和生产构建，不机械增加与本需求无关的浏览器用例。
